# Modelling review & the v2 model

How the Bookings Desk turns form into booking/foul probabilities, what was
wrong with the first model, and what the v2 model (this repo) does about it.

## The original model (v1)

Three layers:

1. **Risk score** — `risk = yc_per90 × 2 + fouls_per90`, a hand-weighted composite.
2. **Season P(card)** — a logistic `p = 1/(1+e^-(a + b·risk))` with slope `b`
   **fixed at 1.1** and only the intercept `a` fitted (anchored so the
   minutes-weighted average player hits the league base rate).
3. **Fixture P(card)** — `season_p × refFactor × derby` (multiplicative).

Fine as a **ranking screen**, but a **miscalibrated forecaster**. The problems,
most impactful first:

| # | Problem | Why it hurts |
|---|---------|--------------|
| a | Referee applied by multiplying the **probability** | `0.72 × 1.3 = 0.94`. On the odds scale it's `0.77`. Overstates by up to ~17pp exactly on the headline picks. |
| b | No **shrinkage** for sample size | 1 yellow in 500 mins reads as 0.18/90. 58 "qualified" players have 450–900 mins where rates are noise. |
| c | Weights/slope **guessed, not fitted** | `×2` and `b=1.1` are hand-picked; only the intercept sees data, so the spread is unvalidated. |
| d | Season-average **composite, not a match model** | A real forecast is event-level: P(≥1 card *this* match) given minutes, opponent, ref, venue. |
| e | No **exposure/minutes** term | A per-90 rate assumes 90 minutes; a 60-minute sub is lower. |
| f | No **opponent** effect on the player number | Opponent fouls-drawn/duel intensity matters (needs the `fw` field). |
| g | No **position** baseline | DMs/full-backs foul & book far more than forwards/keepers. |
| h | **Fouls not forecast** | They're only an input to risk, never an output (over/under markets). |
| i | No **out-of-sample validation** | Calibration was in-sample by construction. |

## The v2 model (implemented)

All the maths is pure and unit-tested in `assets/core.js` (`PLDCore`); the
parameters live in `data/model.js`, generated by `scripts/build-model.mjs`.

### Tier 1 — no new data (live now)

- **Empirical-Bayes shrinkage** (`PLDCore.shrinkRate`): pull each per-90 rate
  toward its **position mean**, weighted by exposure in matches —
  `rate = (events + mean·k) / (matches + k)`, `k = 6` matches. Fixes (b), (g).
- **Log-odds referee/derby** (`PLDCore.contextProb` / `scaleOdds`): multiply the
  **odds**, not the probability. Fixes (a).
- **Calibration metrics** (`PLDCore.brier`, `logLoss`, `reliability`): the Model
  Track Record now reports Brier and log-loss over scored picks vs a base-rate
  baseline. Fixes (i) (as data accrues).

### Tier 2 — fitted logistic GLM

- `PLDCore.glmProb(feats, coef)` scores a logistic with features
  `{yc90, foul90, DF, MF, FW}`. Coefficients live in `data/model.js`.
- **Basis `"season-prior"`** ships today: the prior reproduces the v1 logistic
  but on **shrunk** inputs and re-anchored — an honest, improvable starting
  point, *not* an empirical fit.
- **Basis `"match-fit"`**: run the real fit once match-level data exists —
  ```
  python3 data/harvest_history.py                       # FPL element-summary
  node scripts/build-model.mjs --fit data/match_history.json
  node scripts/backtest.mjs                             # prove it helps
  ```
  The fitter is IRLS (Newton-Raphson); the backtest walks forward gameweek by
  gameweek and reports out-of-sample Brier/log-loss for base vs prior vs a
  weekly refit. Fixes (c), (d), (g); (e)/(f) come in as features are added.

### Tier 3 — fouls forecast + two-stage card

- **Expected fouls** = `foulRate90 × expMinutes/90` (`PLDCore.expectedFouls`).
- **Over/under** via a **Negative-Binomial** tail (`PLDCore.nbTailProb`,
  overdispersed Poisson) → P(fouls over 1.5 / 2.5). Fixes (h).
- **Two-stage card** (`PLDCore.cardProbFromFouls`): mechanistic —
  `P(card) = 1 − exp(−E[fouls] × hazard)`, where `hazard` is the league
  cards-per-foul (anchored to the base rate) scaled by the referee. Surfaced in
  the player profile as a cross-check against the logistic.

### Referee strictness from two signals (cards per foul)

The referee multiplier used to be `clamp(ypg / league_avg_ypg, 0.75, 1.30)`.
Yellows per game is contaminated: an official shows more cards partly because
the fixtures he draws are more foul-heavy, and the desk **already** models each
club's foul and card propensity separately — so ypg alone double-counts the
teams.

`PLDCore.refCardFactor(ref, league, opts)` now blends two ratios, each against
the league average:

- **ypg ratio** — yellows per game, as before;
- **cpf ratio** — **cards per foul**, which divides out the foul volume in front
  of him and isolates how readily he cards the same offence.

They are combined as a weighted geometric mean (the natural average of ratios,
neutral at 1.0), equal weight by default, then clamped to `[0.75, 1.30]`. With
`cpf` absent the function returns the ypg-only ratio, so the shipped model is
bit-identical until a refs refresh harvests fouls — verified in the browser.

The fouls come from `HF`/`AF` in the **same** football-data.co.uk match records
that already supply the card counts, so this adds no new data source, no key and
no scraping: `data/build_refs.py` now aggregates them into `fpg` (fouls per
game) and `cpf` (yellows per foul) per official, and `data/build_pl_data.py`
carries both through the REFS block. Matches whose row lacks fouls still count
toward cards; the cpf denominator is pro-rated over the subset that had them.

Worked example from the test fixture: two officials on effectively the same card
rate (4.00 vs 3.94 yellows/game) separate cleanly on cards per foul — 0.133 vs
0.219 — i.e. one is reaching for the card roughly 64% more readily per foul,
which the raw rate hides entirely.

### Recency-weighted fit (recent form counts more)

The match-level GLM fit weights each match row by **`0.97^(gameweeks in the
past)`** (`PLDCore.recencyWeight`, `data/model.js` `recencyDecay`), so recent
form counts for more than early-season noise — mirroring the match-model
recency decay on gameweekedge.co.uk. It applies in `scripts/build-model.mjs`
(the shipped fit) and in `scripts/backtest.mjs`'s weekly refit, so the
walk-forward score reflects the same weighting the live model uses. With no
gameweek on a row the weight is uniform (a no-op), so the season-prior basis
is unchanged.

### Game state, from a vendored match model (2026-08-04)

The desk has never had a view on the match its cards are shown in, so
`PLDCore.chaseFactor` — written earlier with the right shape — sat inert with
nothing to feed it. It is now fed by **Plsimulator's** fitted Dixon-Coles
model, vendored weekly into `data/sim_model.js` by
`scripts/build-sim-model.mjs` and evaluated by `PLDCore.simFixture`:

    lambda_home = BASE_H x attack(home) x defence(away) x homeAdv(home)
    lambda_away = BASE_A x attack(away) x defence(home)

then a Poisson product over an 11x11 scoreline grid with the Dixon-Coles
low-score correction on 0-0 / 0-1 / 1-0 / 1-1, normalised. This is a port, not
a reimplementation: it is `plsim/models.py` function for function, including
the one-sided home-advantage term and the 10-goal cap, and
`tests/test-core.mjs` pins it to frozen output from the Python so drift fails
CI rather than going unnoticed.

**What it feeds, and the correction that mattered.** The factor takes the
player's own side's *expected result share*, `P(win) + P(draw)/2`, not its win
probability. The distinction is not cosmetic. `chaseFactor` is neutral at 0.5,
but a win probability cannot average 0.5 in a three-way market — the draw takes
about a quarter of the mass, so the mean is near 0.37. Fed raw, an evenly
matched fixture returns ×1.013 and ×1.068 — *both sides marked up* — which
adds a few percent to every player's number league-wide on no evidence and
drags the model off the base rate the logistic is anchored to. Result share is
0.5 on a level fixture and the two sides' factors are exact mirror images about
1.0, so the mean factor across all 380 orderings is 1.000000: a mismatch
**redistributes** card risk between the sides rather than manufacturing it.

Applied on the log-odds scale via `contextProb` alongside the referee, derby
and venue factors. Observed range on the shipped ratings is ×0.887–×1.113
against a ×0.85–×1.20 clamp, so the clamp guards a bad input rather than
shaping normal output.

**Closeness, computed but not wired.** The same grid gives `P(margin <= 1)`,
shown on each fixture card as `tight`. It is the better closeness signal and
the natural replacement for the hardcoded `DERBIES` list — cards follow games
that stay live, not historic rivalries — but booking heat still uses the derby
list, because changing what orders the fixture list is a decision for
`scripts/backtest.mjs`. Same discipline as the hazard model: available beside
the shipped number until a backtest justifies the swap.

**Failure modes are all neutral.** A fixture the simulator has not rated, a
missing `data/sim_model.js`, or a service worker serving a stale `core.js` each
leave every factor at 1.0 — the pre-wiring behaviour — rather than substituting
an average match.

## The calibration loop (server-verified accuracy)

The **Model Track Record** card self-scores in each visitor's browser. On top
of that, a server-side loop grades the model **in the open**, aggregated across
everyone — parity with Gameweek Edge's P5 prediction log:

- **`supabase/plb_predictions.sql`** — a service-role-only table (RLS on, no
  policies): one row per `(season, gw, element)` with the forecast season
  `pcard` and, once the gameweek finishes, `carded` (1/0).
- **`netlify/functions/log-predictions.js`** — a scheduled (`@hourly`) function.
  Before each deadline it logs the upcoming gameweek's season P(card) for every
  player with a fixture; once a gameweek finishes it backfills who was actually
  booked from the FPL result feed (`event/{gw}/live/`). It **reuses the shipped
  pure maths** (`assets/core.js` + `data/model.js` + `data/pl_data.js`, bundled
  via `included_files`) rather than re-implementing the model, so what is graded
  is exactly what the app shows — the referee-independent season P(card) (the
  per-fixture referee scaling is a client-local assignment and can't be graded
  server-side).
- **`netlify/functions/model-calibration.js`** — a public read returning only
  **aggregates**: sample size, observed booking rate, Brier vs a base-rate
  baseline, log-loss, a reliability curve, and the top-20-per-gameweek hit rate.
  The Guide shows it as **Live prediction accuracy** once the loop has graded a
  gameweek.

Both talk to Supabase over PostgREST with the service-role key (the same
dependency-free pattern as `insights.js`). The feature is optional: with no
`SUPABASE_SERVICE_ROLE_KEY` the logger no-ops and the card stays hidden.

## The under-dispersion fix, September 2026

**What was wrong.** The in-page backtest ranked well and priced low: at the
headline threshold (a side taking 2+ yellows) it predicted **53.5%** on average
against **59.1%** observed, while discriminating properly — top decile 35.9
points above the bottom. Ranking well and pricing low is the signature of a
right mean pushed through a distribution of the wrong shape.

**The measurement.** Team yellow counts over 2025/26's 760 team-matches run
**variance 1.663 on mean 1.874** — a dispersion of **0.888**. They are
*under*-dispersed, and a Poisson assumes variance equals mean, so it puts too
much weight on nought and one and prices the "2 or more" tail low. The desk had
no way to say this: `nbTailProb` only ever *widens* a Poisson, and its own
under-dispersed branch hands back `size = Infinity`, which is Poisson again.

**The fix.** A binomial is under-dispersed by construction — variance
`n·p·(1−p)` against mean `n·p`, so dispersion is `(1−p)`. Moment-matching gives
`p = 1 − phi` and `n = mu / p`. `n` must be whole, and rounding it moves the
mean, so `p` is re-solved as `mu / n` afterwards: the mean lands exact and the
dispersion within ~0.002. Calibration lives on the mean. Shipped as
`PLDCore.udTailProb`, which falls through to Poisson if the dispersion is ever
not below one rather than clamping and lying about the input.

**Why a season constant rather than a per-fold refit.** Ten walk-forward folds
of 76 team-matches give in-fold dispersions from 0.67 to 1.21 — one fold reads
*over*-dispersed — which looks unstable. It is not. Simulating 4,000 seasons
from a **fixed** 0.888 puts a fold at or above 1.21 in **12%** of them and an
in-fold standard deviation at or above the observed 0.170 in **13%**. Neither
is unusual; the scatter is what this sample size does. The expanding window a
walk-forward fit actually sees never leaves **0.84–0.95** (sd 0.037) and is
never above one. So the dispersion is fitted once and held, rather than
re-estimated off a handful of matches — which would fit noise and occasionally
invert the correction.

**What it bought, and what it did not.**

| Threshold | predicted before | after | observed |
|---|--:|--:|--:|
| 1+ yellows | 82.1% | **83.8%** | 84.5% |
| 2+ yellows | 53.5% | **54.8%** | 59.1% |
| 3+ yellows | 28.6% | 28.4% | 29.2% |

Discrimination is unchanged to the last digit, as a monotone change of tail
must leave it. Brier is materially unmoved and the verdict is still
**indistinguishable from the baseline at all three thresholds** — the interval
spans zero everywhere, exactly as before.

**So the Poisson link was about a quarter of the bias, not all of it.** The
README previously attributed the whole 5.6-point gap to it; the measurement
says 1.3 points. The remaining ~4.3 points at the headline threshold is the
**mean itself running low**, not the shape around it, and that is a different
fix. A one-parameter walk-forward logit shift was evaluated on top and is
**not** shipped: it improves the headline threshold (Brier 0.2451 → 0.2436,
predicted 54.8% → 57.7%) and makes both others worse (1+ 0.1351 → 0.1357, 3+
0.2013 → 0.2029). Buying the threshold you quote by degrading the two you also
publish is the kind of trade this file exists to refuse.

**Scope.** This is the team-level tail the backtest scores. The per-player card
model is untouched and was already calibrated — `check-models.mjs` reports the
Premier League pricing 15.8% against 15.8% observed, with no player above 43%
against the 55% ceiling.

## Honesty boundary

Tier 1 and Tier 3 are **fully data-grounded** from the shipped season data. The
Tier-2 **coefficients** ship as a **season-derived prior** (`basis:"season-prior"`)
because an empirical match-level fit needs history that the FPL API provides but
that isn't harvestable from every environment. The full fitting + backtest
machinery is implemented and unit-tested; running the harvest flips the model to
`"match-fit"` and the app shows the basis on the Model Track Record card.
